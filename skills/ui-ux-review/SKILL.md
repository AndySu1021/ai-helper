# UI/UX 審核流程

## 輸入需求
- requirements 文件（文字、Word、PDF 或 Markdown）
- prototype（截圖、設計稿或 HTML 檔）
- 若使用者有指定審核範圍或重點，以使用者的指示為準

若缺少任一項，先向使用者索取，不要自行假設內容。

## 執行步驟

### 1. 解析 requirements
擷取並整理成以下清單，供後續比對：
- 目標使用者與使用情境
- 功能性需求（逐條編號）
- 非功能性需求（效能、可及性、平台限制等）
- 明確的限制與排除事項
- 文件中模糊或互相矛盾之處（列出，並註明採用的假設）
- **支援平台**：從 requirements 擷取目標平台清單（例：桌機、手機、平板、PWA、WebView）；若未明確列出，以 `AskUserQuestion` 詢問，不可自行假設

### 2. 檢視 prototype
- 逐頁或逐個流程檢視
- 記錄每個畫面的主要功能與操作路徑
- 若為 HTML，可讀取結構與樣式以判斷層級與互動

### 3. 比對與評估

每個 requirement 標記為：✅ 符合、⚠️ 部分符合、❌ 未符合、➖ 未見於 prototype。

依以下面向逐一檢查，每個面向的問題都應對應到 requirement 編號或公認的 UX 原則：

#### 3a. 資訊架構與導覽
- 頁面層級與麵包屑是否清楚
- 主要動線步驟數是否合理（超過 5 步需說明）
- 返回/取消路徑是否存在

#### 3b. 視覺層級與排版
- 字級、間距、對比度
- 主要行動按鈕是否視覺突出
- 色彩系統是否一致（同功能使用同顏色，不隨頁面改變）
- Spacing 是否遵循固定倍數系統（4px / 8px grid）

#### 3c. 互動狀態完整性
需逐一確認以下狀態是否有對應設計：
- Default / Hover / Focus / Active / Disabled
- Loading（skeleton 或 spinner）
- Success / Error（含錯誤訊息位置與措辭）
- Empty state（列表為空、搜尋無結果）
- Partial failure（部分資料載入失敗）

#### 3d. 錯誤處理 UX
- 錯誤訊息是否以使用者語言描述（非技術錯誤碼）
- 表單是否有 inline validation，錯誤標示在欄位旁而非頂部
- 操作失敗後是否提供明確的復原路徑（重試、返回、聯繫支援）
- 破壞性操作（刪除、送出）是否有確認步驟

#### 3e. 多平台與響應式（RWD）
若 requirements 列有多個目標平台，逐平台檢查：

**斷點與版面**
- 是否定義斷點（建議：mobile ≤ 768px、tablet 769–1024px、desktop ≥ 1025px）
- 各斷點的版面是否描述或展示（單欄 / 多欄切換、側邊欄收合）
- 關鍵元件（表格、表單、導覽列）在小螢幕是否有替代設計

**觸控適配**
- 觸控目標最小 44×44pt（iOS HIG）/ 48×48dp（Material）
- 滑動手勢與點擊行為是否衝突（例：水平滑動元件內嵌在垂直捲動頁面）
- 下拉選單、tooltip 等 hover-only 互動是否有觸控替代方案

**平台差異**
- iOS Safari：底部安全區（safe area inset）、100vh 問題、`position: fixed` 行為
- Android WebView：字體縮放、鍵盤彈出導致版面壓縮
- PWA / 全螢幕模式：狀態列顏色、splash screen、離線提示

**跑版風險清單**
針對以下常見跑版情境逐一確認：
- 長文字（使用者名稱、商品標題）是否有截斷或換行規則
- 多語言字串伸縮（中文 vs 英文字串長度差異可達 2–3 倍）
- 圖片比例不符時的 fallback（object-fit、佔位圖）
- 數字 / 日期格式在不同 locale 下的寬度變化

#### 3f. 可及性（Accessibility）
- **對比度**：文字與背景對比 ≥ 4.5:1（AA），大文字 ≥ 3:1
- **觸控範圍**：互動元素 ≥ 44×44px
- **鍵盤導覽**：Tab 順序是否合理；所有互動元素是否可用鍵盤觸達
- **Focus 管理**：Modal / Drawer 開啟時 focus 是否移入，關閉時是否回到觸發元素（focus trap）
- **ARIA 語意**：圖示按鈕是否有 `aria-label`；動態更新區域是否有 `aria-live`
- **螢幕閱讀器**：裝飾性圖片是否 `alt=""`；表單 label 是否正確關聯

#### 3g. 效能感知
- 頁面初始載入是否有 skeleton screen 或 loading placeholder
- 圖片是否預期使用 lazy loading（首屏以外）
- 過場動畫時長建議：micro-interaction ≤ 200ms，頁面轉場 ≤ 400ms；超過需說明理由
- 大量資料（列表、表格）是否有分頁或虛擬捲動設計

#### 3h. 設計一致性
- 相同功能的元件是否使用相同樣式（主按鈕、次要按鈕、危險操作）
- 用語是否一致（同一動作不出現「刪除」和「移除」混用）
- Icon 風格是否統一（同一套 icon set，不混用不同風格）

### 4. 產出報告

將報告寫入 `ui-ux-review.md`，固定使用以下結構：

#### 1. 總覽
- 審核範圍、使用的 requirements 版本、prototype 版本
- 目標平台清單
- 整體結論（1–2 句）
- 嚴重度匯總：高 X 項 / 中 X 項 / 低 X 項

#### 2. Requirements 符合度
| 編號 | Requirement | 狀態 | 對應畫面 | 備註 |
|---|---|---|---|---|

#### 3. 問題清單
| # | 面向 | 位置 | 問題 | 依據 | 嚴重度 | 修改建議 |
|---|---|---|---|---|---|---|

面向對應 3a–3h 的代碼（例：`3e-RWD`、`3f-A11y`）。

嚴重度定義：
- 高：阻礙核心流程、違反必要需求、或在目標平台造成跑版 / 無法操作
- 中：降低效率或體驗，但可完成任務；或僅在特定平台重現
- 低：細節優化、一致性問題

#### 4. 多平台風險摘要（若有多平台需求）
針對每個目標平台列出：已確認問題 / 潛在風險 / 需進一步測試的項目。

#### 5. 做得好的地方
2–3 點即可。

#### 6. 優先處理順序
依影響程度列出前五項。

#### 7. 待確認事項
列出需要產品或設計方確認的問題。

## 注意事項
- 所有判斷都要對應到 requirement 或公認的 UX 原則，避免主觀偏好
- 不確定的地方標註為「待確認」，不要猜測
- 修改建議要具體可執行，例如「將按鈕高度提高到 48px」，而非「讓按鈕更明顯」
- 多平台問題若無法從靜態 prototype 判斷，列入「待確認事項」並說明需在哪個裝置/瀏覽器實機驗證
- 報告預設以繁體中文撰寫，術語可保留英文原文
