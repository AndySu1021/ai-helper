# UI/UX 審核流程

## 輸入需求
- requirements 文件（文字、Word、PDF 或 Markdown）
- prototype（截圖、設計稿或 HTML 檔）
- 若使用者有指定審核範圍或重點，以使用者的指示為準

若缺少任一項，先向使用者索取，不要自行假設內容。

## 執行步驟

### 1. 解析 requirements
擷取並整理成以下清單，供後續比對：
- 目標使用者與使用情境
- 功能性需求（逐條編號）
- 非功能性需求（效能、可及性、平台限制等）
- 明確的限制與排除事項
- 文件中模糊或互相矛盾之處（列出，並註明採用的假設）

### 2. 檢視 prototype
- 逐頁或逐個流程檢視
- 記錄每個畫面的主要功能與操作路徑
- 若為 HTML，可讀取結構與樣式以判斷層級與互動

### 3. 比對與評估
每個 requirement 標記為：✅ 符合、⚠️ 部分符合、❌ 未符合、➖ 未見於 prototype。

依以下面向檢查 UI/UX：
- 資訊架構與導覽
- 視覺層級與排版（字級、間距、對比度）
- 操作流程（步驟數、卡關點、按鈕位置與大小）
- 回饋與錯誤處理
- 可及性（WCAG 對比度、觸控範圍 44px 以上）
- 元件與用語的一致性

### 4. 產出報告
將報告寫入 `ui-ux-review.md`，固定使用以下結構：

### 1. 總覽
- 審核範圍、使用的 requirements 版本、prototype 版本
- 整體結論（1–2 句）

### 2. Requirements 符合度
| 編號 | Requirement | 狀態 | 對應畫面 | 備註 |
|---|---|---|---|---|

### 3. 問題清單
| # | 位置 | 問題 | 依據 | 嚴重度 | 修改建議 |
|---|---|---|---|---|---|

嚴重度定義：
- 高：阻礙核心流程或違反必要需求
- 中：降低效率或體驗，但可完成任務
- 低：細節優化

### 4. 做得好的地方
2–3 點即可。

### 5. 優先處理順序
依影響程度列出前五項。

### 6. 待確認事項
列出需要產品或設計方確認的問題。

## 注意事項
- 所有判斷都要對應到 requirement 或公認的 UX 原則，避免主觀偏好
- 不確定的地方標註為「待確認」，不要猜測
- 修改建議要具體可執行，例如「將按鈕高度提高到 48px」，而非「讓按鈕更明顯」
- 報告預設以繁體中文撰寫，術語可保留英文原文
