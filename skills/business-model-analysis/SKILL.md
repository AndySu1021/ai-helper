# 商業模式分析

## 使用方式

```
/business-model-analysis <ticket-id 或專案路徑>
/business-model-analysis          # 不指定則從當前目錄讀取輸入，報告寫入 tmp/business-model-analysis.md
```

## 輸出路徑

從 `$ARGUMENTS` 解析目標：
- 若有指定（如 `PROJ-123` 或 `path/to/project`）：報告寫入 `tmp/<ARGUMENTS>/business-model-analysis.md`，輸入文件從 `tmp/<ARGUMENTS>/` 與指定路徑下尋找
- 若未指定：報告寫入 `tmp/business-model-analysis.md`，輸入文件從當前目錄尋找

目錄不存在時先建立。

---

## 目標
閱讀產品的需求與原型，找出可行的商業模式與獲利方式，逐一評估其可行性、優缺點與風險，並提出驗證方法。產出的分析必須能讓產品負責人直接用來做決策。

## 輸入
1. **requirements.md**：產品需求文件。重點擷取目標使用者、核心問題、主要功能、限制條件與優先順序。
2. **prototype**：原型檔案（可能是圖片、HTML、Figma 匯出、或文字描述）。重點觀察使用流程、付費觸點（如升級按鈕、限制提示、結帳頁）、以及使用者可能產生的價值時刻。

若任一輸入缺漏或無法讀取，請先明確告知使用者，並說明缺少哪些資訊會影響分析。

## 工作流程

### 第一步：理解產品
- 整理產品要解決的核心問題與目標使用者（若有多類使用者，分別列出）。
- 列出使用者從「開始使用」到「獲得價值」的關鍵流程。
- 找出產品中「高價值時刻」（使用者願意付錢的瞬間），例如：節省大量時間、完成高風險任務、取得稀缺資源、提升收入或降低成本。
- 標記原型中已存在或可推測的付費觸點。

### 第二步：產出候選商業模式
依據產品特性，從以下類型中挑選適用的模式，並說明為何適用。不必列出全部，只列與本產品相關者：
- **訂閱制（SaaS）**：按月或按年收費，適合持續使用的工具。
- **免費增值（Freemium）**：基本功能免費，進階功能或額度收費。
- **用量計費（Usage-based）**：依使用次數、資料量、API 呼叫等計費。
- **交易抽成（Marketplace / Commission）**：連結買賣雙方並抽取交易比例。
- **企業授權（Enterprise / Seat-based）**：以團隊或座位數授權，附加客製與支援服務。
- **一次性購買或授權**：買斷或永久授權。
- **廣告與贊助**：依曝光或點擊收費，需評估對體驗的影響。
- **資料或洞察服務**：在合規前提下提供匯總的分析報告。
- **增值服務**：諮詢、導入、培訓、客製開發。
- **生態系或平台費用**：與第三方整合、外掛市集、認證費。

### 第三步：逐一評估
每個候選模式請依以下面向評估，並給出評級（高／中／低）與理由：
- **付費意願**：目標使用者是否有預算、是否願意為此價值付費？
- **價值對應**：收費點是否與使用者獲得的價值一致？
- **營收潛力**：規模化後的收入上限大致如何？
- **獲客成本**：此模式下取得客戶的難度與成本。
- **實作複雜度**：對現有需求與原型的改動程度（例如是否需要帳號系統、計費系統、金流、權限管理）。
- **營運負擔**：客服、合規、維運等持續成本。
- **競爭與替代方案**：使用者目前如何解決此問題？有哪些替代品或免費方案？
- **風險**：法規、隱私、平台依賴、定價敏感度等。

### 第四步：提出建議與驗證方式
- 推薦 1 至 3 個最值得優先嘗試的模式，並說明理由。
- 提出組合策略（例如免費版引流、進階版付費），若適用。
- 針對推薦模式，列出可在上線前驗證的方法，例如：訪談目標使用者、設計定價頁測試點擊率、以「假門測試」（Fake door）觀察升級意願、或小規模預購。
- 指出需要向產品團隊確認的關鍵問題（例如：目標市場規模、使用者付費能力、是否有企業客戶）。

## 輸出格式

依「輸出路徑」規則將報告寫入對應的 `tmp/` 目錄，使用繁體中文，依以下結構撰寫：

1. **產品摘要**（3 至 5 句）
2. **目標使用者與核心價值**
3. **可能的付費觸點**（從原型中觀察到的）
4. **候選商業模式總覽**（表格：模式名稱、適用理由、整體評級）
5. **各模式詳細評估**（每個模式使用相同面向評估）
6. **建議優先順序**
7. **驗證計畫**
8. **待確認事項**

## 原則
- **不捏造數據**：市場規模、競品價格、轉換率等數字，若需求文件與原型未提供，請明確標示為「假設」或「需外部研究確認」，不要編造具體數字。
- **區分事實與推論**：明確標示哪些是從文件中讀到的，哪些是你的判斷。
- **不迴避風險**：每個模式都要列出至少一項主要風險，不只講優點。
- **以產品為中心**：建議必須與需求文件中的功能與原型流程相關，避免泛泛而談的通用商業建議。
- **簡潔可決策**：避免冗長的概念解釋，讓讀者能快速比較並做出決定。
- **需要時可搜尋**：若需要查詢同類產品的定價或市場資訊，應使用網路搜尋取得最新資料，並附上來源。
