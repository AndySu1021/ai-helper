# Refactor — Go 程式碼重構

在不改變外部行為的前提下，對指定的 Go 程式碼進行結構性改善。每次只做一類改動，小步驗證，確保每步都能通過 `go build` 與 `go test`。

## 使用方式

```
/refactor <目標檔案或描述>
```

---

## 核心原則

> **行為不變**：重構期間公開 API 的簽名不可改變，外部可觀察行為必須與重構前完全相同。  
> **小步進行**：每次只做一類改動（例如只抽函式、或只改命名），每步都驗證 build 與 test。  
> **不順手修 bug**：發現問題另外列出，不在重構過程中混入修復。

---

## 步驟 1：理解目標範圍

從 `$ARGUMENTS` 解析目標（檔案路徑、套件路徑、函式名稱，或自然語言描述）。

若目標不夠明確（例如只說「整理一下」），以 `AskUserQuestion` 詢問：
- 目標檔案或套件路徑
- 重構目的（提高可讀性 / 消除重複 / 拆分職責 / 其他）

---

## 步驟 2：閱讀程式碼

依序閱讀以下內容，**全部閱讀完才開始動手修改**：

1. **目標檔案**：完整讀取，不只看 diff 或片段
2. **同套件的其他 `.go` 檔案**：了解套件內部結構與既有慣例
3. **主要呼叫端**：用 `Grep` 找出引用目標函式或型別的檔案，至少讀前 3 個

```bash
# 找同套件其他檔案
find <package_dir> -name '*.go' -not -name '*_test.go'

# 找公開符號的所有引用（大寫開頭）
grep -rn '<SymbolName>' --include='*.go' .
```

閱讀完成後，條列出以下資訊後再繼續：
- 目標程式碼的現有結構摘要（主要函式、型別、職責）
- 識別出的重構機會（配合使用者目的）
- 需要特別注意的並行相關程式碼（goroutine、channel、mutex）

---

## 步驟 3：確認測試覆蓋

```bash
# 確認是否有對應的 _test.go
find <package_dir> -name '*_test.go'

# 執行現有測試，記錄 baseline
go test ./... -v 2>&1 | head -60
```

**若目標套件沒有任何測試檔案**，停止並提示：

```
⚠️  風險提示：<package> 下找不到測試檔案。

重構在沒有測試的情況下進行，無法自動驗證行為是否改變。

建議先補上能鎖定現有行為的測試，再繼續重構。
可考慮的測試策略：
- 針對公開函式寫表格驅動測試（table-driven tests）
- 針對關鍵路徑的輸入輸出寫 golden test

是否在沒有測試的情況下繼續？（有風險）
```

以 `AskUserQuestion` 詢問是否繼續。若使用者選擇繼續，在最終輸出的「風險」區段標注此事項。

---

## 步驟 4：制定重構計畫

根據步驟 2 的分析與使用者目的，列出重構步驟清單。每個步驟為一類改動：

| 步驟 | 改動類型 | 目標 | 影響符號 |
|------|---------|------|---------|
| 4.1  | 抽出函式 | `processOrder` 中的驗證邏輯 → `validateOrder` | 內部 |
| 4.2  | Guard clause | `handleRequest` 深層巢狀 → 提前 return | 內部 |
| ...  | ... | ... | ... |

**若涉及以下情境，先停下來問我再繼續**：
- 修改公開符號（大寫開頭的函式、型別、方法、欄位）→ 先用 Grep 確認所有跨套件引用
- 並行相關程式碼的結構改動（goroutine、channel、mutex 的使用方式可能改變）
- 拆分或合併 struct / interface 的欄位或方法

---

## 步驟 5：逐步執行重構

**每個子步驟的執行順序**：

1. 修改程式碼
2. 驗證 build：`go build ./...`（若失敗立即還原）
3. 驗證測試：`go test ./...`（若有既有測試失敗立即還原）
4. 確認通過後再進行下一個子步驟

**各類改動的執行準則**：

### 抽出函式
- 新函式放在同一個檔案，除非邏輯明顯屬於另一個關注點
- 名稱遵循套件既有命名慣例
- 不引入新的公開符號，除非使用者同意

### 重新命名
- 只針對使用者指定的符號，不順手改其他命名
- 修改前用 Grep 確認全部引用（包含測試檔）
- 公開符號跨套件引用必須全部一併修改

### 消除重複（DRY）
- 只抽出在**同一套件**中出現 2 次以上的相同邏輯
- 不引入跨套件的新共用工具，除非使用者同意

### Guard clause 取代深層巢狀
- 保持原有的錯誤處理形式：`if err != nil { return ... }`
- 錯誤包裝維持 `fmt.Errorf(..., %w, err)`，不丟失原始錯誤鏈
- 不改變錯誤回傳的型別或內容

### 拆分大型 struct 或 interface
- 先確認所有引用端，列出影響範圍
- 若影響跨套件的公開型別，停下來詢問使用者
- 拆分後確認 interface 仍由使用端定義，不引入不必要的抽象

---

## 步驟 6：執行完整驗證

所有子步驟完成後，依序執行：

```bash
# 1. 格式化
gofmt -w .
# 若有 goimports 設定
goimports -w .

# 2. 靜態檢查
go vet ./...

# 3. 完整測試
go test ./...

# 4. 若專案根目錄有 .golangci.yml 或 golangci-lint 設定
if [ -f .golangci.yml ] || [ -f .golangci.yaml ]; then
  golangci-lint run ./...
fi
```

若任一步驟失敗，停止並回報失敗原因，不繼續後續驗證。

## 規則

- 只修改使用者指定的檔案或套件，不擴散到其他套件。
- 不修改 `go.mod` 或引入新的第三方依賴。
- 不改變公開 API 的簽名，除非使用者明確同意。
- 並行相關程式碼（goroutine、channel、mutex）的結構改動，行為若可能改變先停下來問。
- 錯誤處理維持 `if err != nil { return ... }` 慣用形式，不改成 panic 或隱藏錯誤。
- 錯誤包裝使用 `fmt.Errorf(..., %w, err)`，不丟失原始錯誤鏈。
- 不為了抽象而引入不必要的 interface；interface 應由使用端定義。
- `context.Context` 保持作為函式第一個參數。
- 說明與註解使用繁體中文；程式碼識別名稱與 Go 慣用命名維持英文。
- 每次只做一類改動，小步進行；每步驗證通過才繼續。
- 發現的 bug 另外列出，不混入重構修改。
