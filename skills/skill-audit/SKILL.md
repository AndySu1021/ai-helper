# Skill Audit — Skill 品質審查

逐一審查指定的 SKILL.md，從邏輯正確性、token 效率、AI 可讀性三個面向產出問題清單與修改建議。

## 使用方式

```
/skill-audit <skill 名稱或路徑>
/skill-audit          # 不指定則審查 skills/ 下所有 SKILL.md
```

---

## 步驟 0：確認審查目標

從 `$ARGUMENTS` 解析目標：

- 若有指定名稱（如 `code-review`）：讀取 `skills/<名稱>/SKILL.md`
- 若有指定路徑（如 `skills/code-review/SKILL.md`）：直接讀取
- 若未指定：用 `Glob` 找出 `skills/*/SKILL.md`，列出清單後全部審查

若目標檔案不存在，停止並告知使用者。

---

## 步驟 1：讀取 SKILL.md

逐一讀取每個目標 SKILL.md 的完整內容。

---

## 步驟 2：三面向分析

對每份 SKILL.md 依序執行以下三個面向的檢查。

**提出問題前，必須先確認問題確實存在**：
1. 引用觸發問題的原文片段（段落標題 + 具體文字）
2. 說明為何這段描述有問題（邏輯推導或具體反例）
3. 若無法從原文直接推導出問題，不得提出該問題

不可依「感覺可能有問題」或「慣例上通常這樣寫」做出指摘。

---

### 面向 A：邏輯衝突

檢查指令、流程、規則之間是否互相矛盾或無法同時滿足。

常見模式：
- 步驟順序衝突（後面的步驟假設前面尚未完成的前提）
- 條件互斥但未說明優先順序（「若 X 則 Y」與「若非 X 則 Y」都存在，但 X 的邊界不清）
- 規則與範例不一致（範例行為和規則說明有落差）
- 人工確認點被其他描述隱性允許跳過
- 輸出路徑在不同段落描述不同

---

### 面向 B：高 token 消耗

找出會讓 AI 產生過多輸出或讀取過多內容的寫法。

常見模式：
- 要求「逐一列出所有...」而未給上限（無邊界的列舉）
- 重複要求讀取同一份文件（例如同一檔案在三個步驟各讀一次）
- 報告模板包含大量佔位符欄位，即使沒有發現也要全部輸出
- Agent 被要求「完整重現」或「全文引用」原始文件
- 步驟間資訊重複整理（先摘要再彙整再輸出，三次加工同一資料）
- 並行 agent 數量過多且分工重疊

---

### 面向 C：描述不清 / AI 誤判風險

找出 AI 可能因描述模糊而做出錯誤行為的地方。

常見模式：
- 關鍵詞語義不明確（「適當的」、「必要時」、「若需要」未定義觸發條件）
- 條件句缺少 else 分支（「若 X 則執行 Y」但未說明「若非 X」怎麼辦）
- 優先順序未定義（多個條件同時成立時 AI 不知選哪個）
- 步驟編號不連續或跳號，可能讓 AI 跳過步驟
- 禁止事項描述過於接近正面描述，容易造成方向混淆
- description frontmatter 與實際行為不一致（AI 靠 description 決定何時觸發此 skill）
- 觸發條件描述使用否定句，AI 傾向忽略否定詞

---

## 步驟 3：產出報告

將報告寫入 `skill-audit-<skill 名稱>.md`（單一目標）或 `skill-audit-all.md`（全部目標）。

報告結構：

```markdown
# Skill Audit 報告

審查時間：<YYYY-MM-DD>
審查目標：<skill 名稱或「全部」>

---

## <skill 名稱>

### 總覽
- 邏輯衝突：X 項
- 高 token 消耗：X 項
- 描述不清：X 項
- 整體評估：<健康 / 需要小修 / 需要重寫>

### 問題清單

| # | 面向 | 嚴重度 | 位置（段落或行） | 問題說明 | 原文片段 | 修改建議 |
|---|------|--------|-----------------|----------|----------|----------|

嚴重度定義：
- 高：會導致 AI 執行錯誤動作，或每次執行都浪費大量 token
- 中：偶發誤判，或明顯可優化的 token 使用
- 低：措辭改善，不影響正確性

### 修改優先順序
依嚴重度列出前三項，每項附上一句具體的修改方向。

---
（若有多個 skill，以 --- 分隔）
```

---

## 規則

- **完全唯讀**：不得修改任何 SKILL.md 或其他檔案。
- **必須提出證據**：每個問題都要附上原文片段與邏輯推導或具體反例，才算成立；無法從原文直接推導的問題一律不得提出。
- 每個問題必須引用原文片段，不可只描述「某處有問題」。
- 若某個面向完全沒有發現，明確寫出「無發現」，不可留白。
- 修改建議要具體可執行（例如「將『若需要』改為『若步驟 2 的回傳結果為空』」），不可只寫「請釐清描述」。
